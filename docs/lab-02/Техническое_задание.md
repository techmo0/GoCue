# GoCue — техническое задание

**Лабораторная работа № 2 · версия 1.0 · 28.10.2026**  
Команда «Диалог», группа ПИб-23Э1.  
Проектное решение, а не акт о готовности реализации.

## 1. Назначение и границы

GoCue — локальное Android-приложение, которое хранит намерения пользователя и показывает их при подтверждённом визите в подходящее место. Пользователь задаёт дело и контекст один раз; простое пересечение геозоны не считается достаточным поводом для уведомления.

Целевые пользователи — люди с бытовыми поручениями, привязанными к месту (покупки, аптека, почта). Инициатор и заказчик учебного проекта — команда «Диалог»; внешнего заказчика нет. Цель MVP — проверить цепочку «записал дело → выбрал свой магазин → остановился там → получил общий список → завершил или отложил до следующего визита».

Платформа MVP — Android. Данные хранятся на устройстве; сервер, аккаунт и LLM не требуются. Проверка реальной геозоны запланирована на Samsung Galaxy S25. Доступность, точность и задержки системных событий должны быть проверены экспериментально, а не заявлены как уже достигнутые.

**Не входят в MVP:** iOS, облачная синхронизация, маршрутизация, поиск и автоматическое распознавание магазинов, распознавание текста, календарь, погода, часы работы, автоматическое определение дома, виджет как обязательная часть. Виджет на презентации — возможное будущее дополнение; для срабатывания при визите нужны системные уведомления.

## 2. Термины и роли

| Термин | Значение |
| --- | --- |
| Намерение (Intent) | Дело с названием и состоянием `ACTIVE`, `COMPLETED` или `ARCHIVED`. |
| Физическое место (Place) | Созданная пользователем точка с координатами, радиусом и ролью, например `SUPERMARKET`. |
| Семантическое место | Псевдоним физического места, например `MY_SUPERMARKET`. |
| Визит (Visit) | Отдельное посещение физического места с состоянием `CANDIDATE`, `CONFIRMED` или `ENDED`. |
| Контекст (ContextSnapshot) | Нормализованное описание подтверждённого места и визита; логика намерений не получает GPS напрямую. |
| Подавление | Запрет повторного показа активного намерения в текущем визите после команды «Напомнить в следующий визит». |

Основной актор — **пользователь**. Внешний технический актор — **Android**: сообщает события геозоны и управляет разрешениями и доставкой уведомлений. Серверных акторов в MVP нет.

## 3. Функциональные требования и приоритеты

Приоритеты: **Must** — обязательно для MVP; **Should** — желательно после базового сценария; **Could** — возможно позже. Критерии приёмки даны в разделе 6; номера `AC` и `FR` обеспечивают трассировку.

| ID | Приоритет | Требование | Проверка |
| --- | --- | --- | --- |
| FR-01 | Must | Пользователь создаёт, изменяет и удаляет намерение с непустым названием. Новое намерение получает `ACTIVE`. | AC-01 |
| FR-02 | Must | Пользователь завершает или архивирует намерение; неактивные намерения не участвуют в показе. | AC-02 |
| FR-03 | Must | Пользователь создаёт, изменяет и удаляет физическое место с названием, координатами, положительным радиусом и ролью. | AC-03 |
| FR-04 | Must | Пользователь явно связывает `MY_SUPERMARKET` с одним местом роли `SUPERMARKET`; при смене связи существующие намерения не редактируются. | AC-04 |
| FR-05 | Must | Намерение связывается с требованием `SEMANTIC_PLACE = MY_SUPERMARKET` либо `PLACE_ROLE = SUPERMARKET`; требование не хранит координаты. | AC-04, AC-05 |
| FR-06 | Must | Событие входа создаёт визит-кандидат; уведомления на сыром входе нет. После непрерывного нахождения внутри геозоны не менее 60 секунд визит подтверждается. Порог конфигурируемый для испытаний. | AC-06, AC-07 |
| FR-07 | Must | При подтверждённом визите движок проверяет только активные и не подавленные в этом визите намерения по нормализованному контексту. | AC-05, AC-07 |
| FR-08 | Must | Все подходящие намерения для одного визита/контекста собираются в одно уведомление; повторная оценка не создаёт дубль. | AC-08 |
| FR-09 | Must | Команда «Напомнить в следующий визит» оставляет выбранные намерения активными, подавляет их в текущем `visitId` и допускает показ в новом подтверждённом визите. | AC-09 |
| FR-10 | Must | Завершение, визит, подавление и факт отправленного уведомления сохраняются так, чтобы перезапуск приложения не создавал повтор. | AC-10 |
| FR-11 | Must | Приложение хранит журнал ключевых событий и показывает экран отладки с текущим местом, состоянием визита, подходящими намерениями, подавлениями и причиной последнего уведомления. | AC-11 |
| FR-12 | Must | Режим симуляции позволяет вызвать `ENTER`, `CONFIRM`, `EXIT` без GPS и увидеть тот же результат движка. | AC-12 |
| FR-13 | Must | При отказе/отзыве фоновой геолокации намерения остаются доступны, автоматическое срабатывание недоступно; при отключённых уведомлениях интерфейс объясняет ограничение. | AC-13 |
| FR-14 | Should | При кратком выходе и возврате через границу геозоны в течение 60 секунд сохраняется тот же визит; если возврата нет, визит завершается. Это проектное антидребезговое правило подлежит настройке по испытаниям. | AC-14 |
| FR-15 | Should | Если новое намерение создано уже во время подтверждённого визита, оно появляется в открытом списке, но не порождает второе уведомление той же группы/визита. Если уведомления ещё не было, действует обычная группировка. | AC-15 |
| FR-16 | Should | При удалении места приложение предупреждает о связях; привязка семантического места удаляется, зависимые активные намерения остаются доступными для редактирования, но не срабатывают до новой привязки. | AC-16 |
| FR-17 | Must | Пользователь удаляет сохранённую историю визитов и журнал событий через настройки приватности; действующие намерения и места при этом сохраняются, а активная геозона/текущий визит пересоздаются безопасно. | AC-17 |

**Правило приоритета контекста:** явный выбор `MY_SUPERMARKET` точнее общей роли `SUPERMARKET`. Намерение для `MY_SUPERMARKET` не должно сработать в другом супермаркете; намерение для общей роли может сработать в любом сохранённом месте этой роли. Автоматическое «предпочтение по привычке» в MVP отсутствует.

## 4. Нефункциональные требования

| ID | Приоритет | Требование и измеримый критерий |
| --- | --- | --- |
| NFR-01 | Must | **Приватность:** нет обязательного аккаунта, сервера, выгрузки истории мест и непрерывного GPS-трека. Пользователь может удалить намерения, места, визиты и журнал. Проверка — осмотр разрешений, хранилища и сетевой активности прототипа. |
| NFR-02 | Must | **Детерминизм:** при одинаковых активных намерениях, привязках, состоянии визита и подавлениях движок возвращает одинаковый набор подходящих дел. Проверка — модульные тесты. |
| NFR-03 | Must | **Отсутствие шума:** в 20 симулированных коротких проходах/проездах мимо — 0 уведомлений; в 20 повторных оценках и сценариях перезапуска — 0 дополнительных уведомлений на группу/визит. Это целевые критерии, не измеренный результат. |
| NFR-04 | Must | **Восстановление:** завершённое намерение, явная привязка места и ключ дедупликации сохраняются после принудительного завершения процесса и повторного запуска. |
| NFR-05 | Should | **Быстрый ввод:** медианное время создания типового дела в 10 сценариях с добровольцами — не более 10 секунд; ориентир 2–3 секунды проверяется отдельно и не является обещанием MVP. |
| NFR-06 | Must | **Понятные разрешения:** до запроса фоновой геолокации объяснить цель; при недостаточном разрешении показать недоступные функции и способ исправления. |
| NFR-07 | Must | **Автономность:** создание, просмотр и завершение намерений работают без сети. |
| NFR-08 | Should | **Наблюдаемость:** журнал позволяет восстановить причину показа: место, визит, подходящие намерения и ключ отправки. |

## 5. Основные сценарии использования

| UC | Сценарий | Предусловие | Результат |
| --- | --- | --- | --- |
| UC-01 | Добавить намерение | Приложение доступно | `ACTIVE`-намерение с требованием места сохранено. |
| UC-02 | Настроить свой магазин | Есть физическое место роли `SUPERMARKET` | `MY_SUPERMARKET` указывает на него. |
| UC-03 | Получить список при визите | Есть разрешения, активные дела и подтверждённый визит | Одно уведомление с подходящими делами. |
| UC-04 | Завершить дело | Дело активно | Состояние `COMPLETED`; будущих уведомлений по нему нет. |
| UC-05 | Напомнить в следующий визит | Есть подтверждённый текущий визит | Визитное подавление; дело остаётся `ACTIVE`. |
| UC-06 | Просмотреть причину срабатывания | Есть сохранённые события | Видны место, визит, совпавшие требования и отправка. |
| UC-07 | Протестировать без GPS | Доступен режим симуляции | Те же правила срабатывания без физического визита. |

## 6. Критерии приёмки

| ID | Дано | Когда | Тогда |
| --- | --- | --- | --- |
| AC-01 | Пустой список | Пользователь вводит «Купить батарейки» и выбирает `MY_SUPERMARKET` | Создано одно `ACTIVE`-намерение; пустое название отклоняется. |
| AC-02 | Активное намерение | Пользователь завершает/архивирует его | Состояние изменено, движок больше не возвращает его. |
| AC-03 | Форма места | Указан неположительный радиус или отсутствует название | Сохранение отклоняется; корректное место сохраняется. |
| AC-04 | Два супермаркета A и B | `MY_SUPERMARKET` переназначен с A на B | Намерение с этим псевдонимом совпадает только в B без изменения самого намерения. |
| AC-05 | Требование `MY_SUPERMARKET` и требование общей роли | Подтверждён визит в другом супермаркете | Совпадает только требование общей роли. |
| AC-06 | Вход в геозону | Пользователь сразу покидает её до 60 секунд | Ни визит `CONFIRMED`, ни уведомление не создаются. |
| AC-07 | Активное подходящее намерение | Визит остаётся внутри геозоны не менее 60 секунд | Визит `CONFIRMED`, намерение подходит и может быть показано. |
| AC-08 | Три подходящих намерения | Визит подтверждён и движок оценивается повторно | Отправлено ровно одно групповое уведомление за визит/контекст. |
| AC-09 | Активное дело показано в визите V1 | Пользователь выбирает «Напомнить в следующий визит», затем наступает визит V2 | В V1 повторов нет; в V2 дело снова подходит. |
| AC-10 | Подтверждённый визит и отправленное уведомление | Процесс завершён и запущен вновь | Состояние восстановлено; второго уведомления в том же визите нет. |
| AC-11 | Произошло уведомление | Пользователь открывает журнал/отладку | Показаны место, `visitId`, совпавшие требования и причина уведомления. |
| AC-12 | Устройство не перемещалось | В симуляторе вызваны `ENTER` → `CONFIRM` → `EXIT` | Наблюдается тот же переход состояний и тот же набор подходящих дел. |
| AC-13 | Разрешение геолокации отозвано или уведомления выключены | Пользователь открывает приложение | Управление делами работает; показано корректное ограничение автоматического показа. |
| AC-14 | Подтверждённый визит V1 | `EXIT` и новый `ENTER` разделены менее 60 секундами | Сохраняется V1; повторного уведомления нет. После 60 секунд без возврата V1 завершается. |
| AC-15 | Группа уже показана в текущем визите | Создано новое подходящее дело | Оно видно в открытом списке; нового уведомления этой группы нет. |
| AC-16 | `MY_SUPERMARKET` указывает на удаляемое место | Пользователь подтверждает удаление | Связь удалена; намерения сохранены, но до новой привязки не подходят. |
| AC-17 | Есть история визитов и журнал событий | Пользователь очищает историю | Исторические записи удалены; намерения и места сохранены; повторное уведомление в текущем визите не возникает. |

## 7. Приёмка и условия испытаний

Порядок: модульные тесты чистой логики → симуляция событий и перезапуска → одна реальная геозона на Samsung Galaxy S25. Для реального визита нужно фиксировать разрешения, режим геолокации, время `ENTER`/`CONFIRM`/`EXIT`, состояние приложения и факт доставки уведомления. Задержка событий Android и погрешность определения места не устраняются только кодом приложения: результаты и ограничения фиксируются в протоколе испытаний.

Приёмка MVP возможна после выполнения всех **Must**-требований и соответствующих `AC`, а также документирования известных отклонений реальных геозон. Пункты **Should** принимаются отдельно и не маскируют невыполненные **Must**.
